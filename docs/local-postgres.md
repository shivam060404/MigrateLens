# Local PostgreSQL development

The user-created development database is `MigrateLens` (case-sensitive name) on PostgreSQL 18.4 at `localhost:5433`. The pgAdmin administrative connection uses `postgres`. Existing application databases must not be used by MigrateLens migrations or tests.

Applied setup: `.local/migratelens-development-setup.sql`, generated from Alembic revision `0001_tenant_control` with `scripts/local_development_database_guard.sql` inside the same transaction. It refuses another database or an existing `ml` schema. With user approval, pgAdmin executed it in `MigrateLens` and reported `COMMIT`. Catalog verification returned revision `0001_tenant_control`, 14 application tables, 14 tables with RLS enabled and forced, 14 policies, and `ml_runtime` as NOLOGIN/NOSUPERUSER/NOBYPASSRLS. Do not rerun the initial setup; use subsequent Alembic revisions.

The `ml_runtime` group has no password and cannot log in. The restricted `ml_development` login is provisioned and has an authenticated local smoke check. Never configure the application with the `postgres` administrative URL. Keep credentials outside source control and outside repair execution processes.

For normal future migrations, supply `ML_MIGRATION_DATABASE_URL` through the local environment and run `make PYTHON=python3 migrate`. Use the exact database name `MigrateLens` and port `5433` in that URL. The separate runtime URL is `ML_DATABASE_URL`; it is never a migration fallback.

Live isolation tests require a separate disposable database ending in `_test`, with `ML_TEST_ADMIN_DATABASE_URL` and `ML_TEST_RUNTIME_DATABASE_URL`. Do not point them at `MigrateLens`. Both URLs must use `postgresql+psycopg2`, explicit matching host/port/database, distinct admin and runtime roles, and no URL query overrides. Run `make test-database` only after that database is migrated and its restricted login exists. The suite requires `ML_TEST_DATABASE_DISPOSABLE=yes` and refuses any existing tenant rows before it inserts synthetic data. It leaves those rows for audit; recreate the throwaway database for another run. Do not set this flag for an existing application database.

The agent terminal currently cannot connect to local PostgreSQL because the sandbox denies sockets. pgAdmin access alone does not establish that the automated database tests have passed.

## Dedicated development login (credential configured; connection unverified)

With explicit user approval, pgAdmin ran [the provisioning SQL](../scripts/local_development_login.sql) against `MigrateLens` and reported `COMMIT`. A catalog query confirmed `ml_development` is LOGIN, has no superuser, RLS bypass, create-role, create-database or replication flags, belongs to `ml_runtime`, can connect to `MigrateLens`, and has a NULL password. The script refuses an existing `ml_development` role rather than modifying one, checks the migration and privilege group, and creates a LOGIN with no password, no administrative attributes, and `ml_runtime` membership without grant administration. It sets connection and query time limits. It does not change cluster-wide PUBLIC privileges or restrict access to unrelated databases; local cluster ownership remains the operator's responsibility.

The owner removed an accidentally created `ml` role and set the password on `ml_development`. A fresh pgAdmin catalog query confirmed LOGIN=true, password_configured=true, and `ml_runtime` membership. No password value was read. The owner ran `make db-smoke` in their normal terminal after installing the pinned `.venv` dependencies; it passed the restricted login, inherited grants, and empty tenant scope checks. The agent terminal still receives `Operation not permitted` when attempting to connect to `::1:5433` before authentication. To repeat the check, run `make db-smoke` in a normal local terminal; it prompts privately for the `ml_development` password, checks the exact database and role, inherited runtime grants, and empty tenant visibility before any tenant context. It stores no URL or password. A pass is local authentication and scope evidence, not the full tenant-isolation acceptance suite. Keep the password out of chat, checked-in SQL and command arguments. Local `pg_hba.conf` must require password authentication for this login.

Supply `ML_DATABASE_URL` through a private environment using the SQLAlchemy URL shape `postgresql+psycopg2://ml_development:<percent-encoded-password>@localhost:5433/MigrateLens`. The placeholder is not a credential. The backend reads process environment; it does not automatically load a root `.env` file. Run `make PYTHON=python3 identity-init`, then set `ML_CONTROL_API_ENABLED=true`, `ML_AUTH_MODE=local_token`, and `ML_IDENTITY_PUBLIC_KEY_PATH=.local/identity/public.pem` before `make PYTHON=python3 dev-backend`. Keep the private signing key local and outside repair processes.

Startup now checks runtime-role admission and the declared table catalog before serving the control API; transactions repeat the role check. The catalog check requires 14 declared tables, forced RLS and a named `tenant_scope` policy on each. It does not compare policy expressions and requires live isolation acceptance. This rejects administrative memberships, switched roles and application table owners. It does not replace live RLS tests, schema acceptance, or tenant/membership provisioning; an empty database has no authorized application users.

Privilege behavior follows the official PostgreSQL 18 [role options](https://www.postgresql.org/docs/18/sql-createrole.html) and [privilege inquiry functions](https://www.postgresql.org/docs/18/functions-info.html). Local unit tests use explicit connection doubles; the new role-membership query and provisioning script still require live acceptance.
